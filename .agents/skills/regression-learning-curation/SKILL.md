# Regression Learning Curation

1. Learn only from source-linked evidence: reproduced defects, failed checks, accepted fixes, measured improvements, repeated operator friction, or successful repeated workflows.
2. Separate one-off project preference from reusable Empire behavior. Product-specific lessons stay local unless recurrence and portability are demonstrated.
3. Before changing a skill, capture the failure or desired behavior as a regression/eval when practical.
4. Prefer the smallest durable change: test/eval, documentation clarification, template, routing adjustment, skill refinement, then new skill/agent only when necessary.
5. Every governance/skill/agent/registry/eval change must occur on a reviewable branch/PR, pass Empire Guard/evals, and may not self-approve or bypass owner controls.
6. Preserve previous intent and compatibility unless an explicit migration decision says otherwise.
7. Record why the lesson is generalizable, supporting evidence, affected capabilities, expected improvement, risks, and rollback/removal condition.
8. Never ingest secrets, private client data, personal data, or hidden model reasoning as reusable learning assets.

Deliver a learning proposal or branch change containing regression evidence, minimal improvement, validation result, scope boundary, and rollback path.
